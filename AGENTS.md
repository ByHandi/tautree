# Agent Guidelines & Development Workflow

This document defines the workflow, conventions, and operational rules for AI coding assistants working in this repository (Tautree). Human-facing details live in [CONTRIBUTING.md](CONTRIBUTING.md); this file does not override it.

---

## 1. Task Discovery & Backlog Workflow

1. **GitHub Issues first**:
   - The source of truth for planned work is **GitHub Issues** (`gh issue list --state all`) and the active **milestones** (one per version, e.g. `v0.2.0`). [ROADMAP.md](ROADMAP.md) only summarizes them.
   - Before proposing what to build next or starting work, query the open issues in the current milestone and read the issue body: its checklist is the scope.
2. **Issue keys**:
   - Every issue title is `[TAUTREE-XX] type: short description`, where `type` is the Conventional Commit type (e.g. `[TAUTREE-10] feat: vCard "Save contact" button`). The key is sequential and separate from the GitHub issue number. Find the latest one with:

     ```bash
     gh issue list --state all --search 'TAUTREE in:title' --limit 200 --json title --jq '.[].title' | grep -o 'TAUTREE-[0-9][0-9]*' | sort -t- -k2 -n | tail -1
     ```

3. **Branches**:
   - Branch off `origin/dev` (the integration branch), not `main`: `git switch --no-track -c <type>/TAUTREE-XX-short-description origin/dev`, e.g. `feat/TAUTREE-10-vcard-download`, `fix/TAUTREE-11-embed-height`, `ci/TAUTREE-04-harden-ci`.
   - A small change without an issue can use `<type>/short-description`.
4. **Pull requests**:
   - Every development PR (features, fixes, chores, docs) targets `dev`. `main` only moves through a **release PR** `dev` → `main` when a milestone is complete.
   - `main` is the default branch, so `Closes #N` does **not** link or close issues from a PR into `dev`. Write `Issue: TAUTREE-XX / #N` in the description instead; the maintainer links it in the **Development** sidebar.
   - A release PR `dev` → `main` must list `Closes #N`, one per line, for every issue it ships, so they close on merge.
   - Releases follow [CONTRIBUTING.md § Releasing](CONTRIBUTING.md#releasing): pushing the tag `vX.Y.Z` on `main` runs `.github/workflows/release.yml`, which creates the GitHub Release from CHANGELOG.md. Don't create releases by hand.
   - Put the PR in the issue's milestone and fill in the [PR template](.github/pull_request_template.md).

## 2. Git & Commit Policy (Crucial)

- **Do not commit, push, or open a PR unless the user explicitly asks for it in that turn.** Leave changes in the working tree so the user can review them and commit themselves.
- When asked to open a PR, first check that the branch is committed and pushed, then use `gh pr create --base dev`.
- Commit subjects follow [Conventional Commits](https://www.conventionalcommits.org) (`feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`, `ci:`, optional scope such as `feat(analytics): …`), **without** the ticket key. The key belongs in the issue title, the branch name, and the PR description.
- Don't leave temporary or debug files behind, and report the exact files you modified.

## 3. Architecture & Feature Implementation Order

Features typically cross these layers, in this order:

1. **Data layer** (if needed):
   - Edit `prisma/schema.prisma`, then create a migration with `npm run db:migrate`. Commit the generated migration in `prisma/migrations/`. **Never edit a migration that is already committed.**
   - The Prisma client is generated into `lib/generated/prisma` (gitignored, regenerated by `postinstall`); import the shared client from `lib/db.ts`. Update `prisma/seed.ts` if the change affects seed data.
2. **Domain logic** in `lib/`:
   - Pure, testable functions (links, profile, analytics, social, embed, fonts, button-style, themes, username, admin). New business rules belong here, not in components or actions.
   - Add or update the colocated Vitest test (`lib/<module>.test.ts`). Security-sensitive helpers (`isLinkLive`, `isProfilePublic`, thumbnail/embed validation, anything touching access control or gating) must stay well covered, including a test that the unsafe case is rejected.
3. **Server actions & route handlers**:
   - Server actions live in an `actions.ts` next to the route that uses them (e.g. `app/(dashboard)/dashboard/links/actions.ts`). Check the session and ownership in every action; never trust IDs from the client.
   - Route handlers live under `app/api/` (e.g. `app/api/r/[id]` for link redirects).
4. **Components**:
   - Shared components in `components/`, shadcn-style primitives and form wrappers in `components/ui/`. Components used by a single route sit next to that route in `app/`.
5. **Routes** in `app/`: `(dashboard)` for the signed-in dashboard, `(auth)` for sign-in, `admin`, `onboarding`, and the public profile `[username]`.

**Conventions**:

- Render icons with the `Icon` component (`components/ui/icon.tsx`, lucide `DynamicIcon`, kebab-case `name`), not per-icon imports.
- Prefer the existing form wrappers (`InputText`, `InputSelect`, `InputSwitch`, `DatePicker`, …) over raw inputs.
- Add new shadcn components with `npx shadcn@latest add <component>`; don't hand-copy them.
- Analytics are intentionally privacy-friendly: no IP addresses, cookies, or user agents. Don't introduce tracking that identifies visitors.
- Public pages, OG images, and redirects must respect the same gating (suspended users, inactive or scheduled links).

**Complexity limits** (ESLint, so `npm run lint`, the pre-commit hook, and CI all enforce them):

| Rule                           | Max |
| ------------------------------ | --- |
| `complexity` (cyclomatic)      | 15  |
| `sonarjs/cognitive-complexity` | 15  |

When a function grows past a limit, split it into well-named helpers (a pure function, a lookup table instead of a ternary chain, a module-level subcomponent for a block of JSX) instead of raising the limit or disabling the rule. `components/ui` is exempt from `complexity` only; `lib/generated/**` is ignored.

## 4. Language & Documentation Rules

- **English for everything in the repo**: code, comments, log and error messages, commit messages, issues, PR descriptions, and UI copy, even when chatting with the user in another language.
- **User docs stay bilingual**: `README.md` / `README.id.md` and `ROADMAP.md` / `ROADMAP.id.md` are updated together.
- **Changelog**: add user-visible changes under `## [Unreleased]` in [CHANGELOG.md](CHANGELOG.md) in the same PR. Internal refactors, CI, and tooling changes don't get an entry.
- **Roadmap**: check off the item (and add the issue link if it's missing) in both `ROADMAP.md` and `ROADMAP.id.md` in the PR that completes it.
- **Environment**: document new environment variables in `.env.example` and the README.
- **Decisions**: when a choice is genuinely the user's (a trade-off, scope), ask with a few concrete options and a recommendation instead of guessing.

## 5. Verification & Quality Gates

Always verify changes locally before concluding work. Run the same checks as CI (`.github/workflows/ci.yml`), also listed in [CONTRIBUTING.md § Before you open a PR](CONTRIBUTING.md#before-you-open-a-pr):

```bash
npx prettier --check .
npm run typecheck
npm run lint
npm test
npm audit --omit=dev --audit-level=critical
npm run build
```

If the change touches dependencies or Docker, also run `docker build --target runner .` (and `docker compose config --quiet` for `docker-compose.yml`). No database is needed for any of these.

If CI changes, follow `ci.yml` over this list. When reporting, say what you could **not** verify, e.g. UI flows not checked in a browser because they need a running database.
